# CLAUDE-storefront.md — Ruedee Jewelry หน้าเว็บสินค้า

เอกสารนี้ใช้คู่กับ `CLAUDE.md` (ระบบ CRM บน LINE) แต่เป็นคนละแอป คนละ deploy
ไฟล์นี้ว่าด้วยเว็บหน้าบ้านที่ `ruedeejewelry.com` เท่านั้น

---

## 1. เป้าหมายเดียวของเว็บนี้

**ทำให้ลูกค้าเห็นของจริงเร็วที่สุด แล้วทักแชทถามเรื่องชิ้นนั้นได้ในคลิกเดียว**

เว็บนี้ไม่ได้ปิดการขายด้วยตัวเอง ไม่มีตะกร้า ไม่มีการชำระเงิน หน้าที่ของมันคือพาคนไปที่แชท LINE พร้อมข้อมูลว่าสนใจชิ้นไหน
ทุกการตัดสินใจออกแบบให้วัดด้วยคำถามเดียว: อันนี้ทำให้คนเห็นของเร็วขึ้นและทักง่ายขึ้นไหม ถ้าไม่ ตัดทิ้ง

## 2. สิ่งที่ต้องเลิกทำ (จากเว็บเดิม)

ข้อเหล่านี้เป็นข้อห้าม ไม่ใช่ข้อแนะนำ:

- **ห้ามใช้การ์ดพลิก (flip card)** เป็นทางเข้าหมวดสินค้า
- **ห้ามใช้ modal เป็นหน้าสินค้า** ทุกชิ้นต้องมี URL ของตัวเอง กด back ได้ แชร์ลิงก์ได้
- **ห้ามใช้คารูเซลเป็นวิธีหลักในการดูสินค้าหลายชิ้น** ใช้ grid ที่ scroll ลงได้
- **ห้ามเอาราคา ไซซ์ รหัสสินค้า ไปฝังในรูปภาพ** ทุกอย่างต้องเป็น text จริงใน HTML
- **ห้ามมีข้อความสอนวิธีใช้** เช่น "TAP TO FLIP" หรือ "SWIPE OR TAP ARROWS" ถ้า UI ต้องมีคู่มือ แปลว่า UI ผิด
- **ห้าม autoplay วิดีโอ** และห้ามโหลดไฟล์วิดีโอจนกว่าผู้ใช้จะกดเล่น
- **ห้ามใช้ animation library** (framer-motion และอื่น ๆ) transition ที่จำเป็นใช้ CSS ล้วน

## 3. โครงสร้างหน้า

| URL | หน้าที่ |
|---|---|
| `/` | หน้าแรก — สินค้าใหม่ล่าสุด 8–12 ชิ้น + เรื่องร้านแบบย่อ + ทางเข้าหมวด |
| `/jewelry` | catalog รวมทุกชิ้น มีฟิลเตอร์ |
| `/jewelry/[sku]` | หน้าสินค้าหนึ่งชิ้น เช่น `/jewelry/rg126` |
| `/series` | รวมซีรี่ย์ทั้งหมด |
| `/series/[slug]` | หน้าซีรี่ย์ เช่น `/series/crab` |
| `/about` | เรื่องของร้าน |
| `/faq` | คำถามที่พบบ่อย |
| `/ring-size` | วิธีวัดไซซ์นิ้ว + ลิงก์ไปแอป CRM |

### หมายเหตุเรื่องซีรี่ย์

คอนเซปต์ซีรี่ย์ (เช่น CRAB Episode 50) เป็นจุดแข็งของร้าน ให้เก็บไว้ แต่เป็น **ชั้นที่วางทับ catalog** ไม่ใช่ทางเดียวที่จะเห็นของ
สินค้าหนึ่งชิ้นอยู่ใน catalog เสมอ และอาจอยู่ในซีรี่ย์ด้วยหรือไม่ก็ได้ หน้าซีรี่ย์ดึงสินค้าจากตัวเดียวกัน ไม่ใช่ข้อมูลคนละชุด

## 4. หน่วยพื้นฐานคือ "ชิ้น" ไม่ใช่ "คอลเลกชัน"

สินค้าทุกชิ้นเป็นชิ้นเดียวในโลก มีรหัสของตัวเอง (RG126, RG60 ...) การ์ดสินค้าหนึ่งใบ = ของหนึ่งชิ้น เสมอ

### การ์ดสินค้าต้องแสดง

- รูปหลัก 1 รูป (อัตราส่วนเดียวกันทุกใบ ห้าม layout กระโดด)
- รหัสสินค้า
- ราคา — **ต้องเห็นตั้งแต่ในกริด ไม่ต้องกดเข้าไปดู**
- ไซซ์ (ถ้าเป็นแหวน) และน้ำหนักทอง
- ชนิดพลอย
- ถ้าขายแล้ว: ขึ้นป้าย "ขายแล้ว" **แต่ไม่ลบออกจากเว็บ** ของที่ขายไปแล้วคือหลักฐานว่าร้านทำงานจริง และเป็นตัวอย่างให้สั่งทำแบบเดียวกัน

### หน้าสินค้าเดี่ยวต้องมี

- รูปหลายมุม ซูมได้ รวมรูปใส่บนมือถ้ามี
- ตารางสเปก: ชนิดพลอย น้ำหนักกะรัต สี ชนิดทอง น้ำหนักทอง ไซซ์ ใบเซอร์
- ถ้ามีใบเซอร์ แสดงรูปใบเซอร์ได้
- **ปุ่มทัก LINE ที่พ่วงรหัสสินค้าไปด้วย** (ดูข้อ 5)
- ปุ่มรอง: "อยากได้แบบนี้แต่ไซซ์อื่น" → ทัก LINE พร้อมข้อความสั่งทำ
- สินค้าใกล้เคียง 4 ชิ้น

## 5. ปุ่มทัก LINE (สำคัญที่สุดในเว็บนี้)

ทุกจุดที่มีสินค้า ต้องมีทางทักที่ **บอกได้ว่าสนใจชิ้นไหน** ห้ามมีปุ่มทักแชทลอย ๆ ที่ไม่พ่วงบริบท

- ใช้ลิงก์ไป LINE OA พร้อม query ที่ทำให้ข้อความตั้งต้นเป็น เช่น `สนใจ RG126 ค่ะ`
- ถ้าวิธี prefill ข้อความของ LINE ใช้ไม่ได้ในบางเบราว์เซอร์ ให้ **คัดลอกรหัสสินค้าไปยัง clipboard อัตโนมัติ** ก่อนเปิด LINE แล้วขึ้น toast บอกว่า "คัดลอกรหัส RG126 แล้ว วางในแชทได้เลย"
- ปุ่ม LINE แบบลอยด้านล่างจอ (มีอยู่แล้วในเว็บเดิม ให้เก็บไว้) เมื่ออยู่ในหน้าสินค้าเดี่ยว ต้องพ่วงรหัสชิ้นนั้นด้วย
- CTA ต้องเหมือนกันทั้งเว็บ อย่าให้บางหน้าเป็นปุ่มโทรอย่างเดียว เบอร์โทรเก็บไว้เป็นทางรอง

## 6. ฟิลเตอร์และการค้นหา

ฟิลเตอร์ตามที่คนซื้อพลอยคิดจริง ไม่ใช่แค่แบ่งตามประเภทเครื่องประดับ:

- ประเภท (แหวน / ต่างหู / สร้อยข้อมือ / เข็มกลัด / จี้)
- ชนิดพลอย (ไพลิน ทับทิม มรกต เพชร พลอยสตาร์ ...)
- ช่วงราคา
- ชนิดทอง (ทอง 90 / 18K / ทองคำขาว)
- ไซซ์แหวน (40–70)
- สถานะ (มีของ / ขายแล้ว)

ข้อกำหนด:
- **ฟิลเตอร์ต้องอยู่ใน URL เป็น query param** เช่น `/jewelry?stone=sapphire&max=60000` เพื่อให้แชร์ลิงก์ได้ กด back ได้ และแอดมินส่งลิงก์ผลลัพธ์ให้ลูกค้าในแชทได้
- กรองแล้วต้องไม่ reload ทั้งหน้า แต่ก็ห้ามใช้ JS ก้อนใหญ่ ถ้าจำนวนสินค้าไม่เกินหลักร้อย ให้ส่งข้อมูลทั้งหมดมาครั้งเดียวแล้วกรองฝั่ง client
- มีช่องค้นด้วยรหัสสินค้าตรง ๆ เพราะลูกค้าที่เห็นของจาก IG/TikTok จะจำรหัสมา

## 7. Performance budget (ตัวเลขที่ต้องผ่าน)

วัดบนมือถือระดับกลาง เครือข่าย 4G ไม่ใช่บนเครื่อง dev:

| ตัวชี้วัด | เพดาน |
|---|---|
| LCP | ≤ 2.5 วินาที |
| CLS | ≤ 0.05 |
| JS ที่ส่งไปหน้า catalog | ≤ 120 KB (gzip) |
| รูปหนึ่งใบในกริด | ≤ 80 KB |
| รูปใหญ่ในหน้าสินค้า | ≤ 250 KB |
| จำนวนรูปที่โหลดตอนเปิดหน้า catalog | ไม่เกินที่เห็นในจอแรก |

ถ้าเพิ่ม feature ใดแล้วตัวเลขเกิน ให้ตัด feature ไม่ใช่ขยับเพดาน

### วิธีทำให้ถึงเป้า

- ทุกหน้าเป็น **static / ISR** ห้าม fetch ข้อมูลสินค้าตอน runtime ฝั่ง client
- รูปผ่าน `next/image` ทั้งหมด ส่ง AVIF เป็นหลัก WebP เป็น fallback
- ใส่ `priority` เฉพาะรูปแรกที่เห็นในจอ ที่เหลือ lazy load
- ต้องมี blur placeholder ทุกรูป เพื่อไม่ให้หน้ากระตุกและ CLS เกิน
- กำหนดอัตราส่วนรูปตายตัว จองพื้นที่ไว้ก่อนรูปมา
- **ฟอนต์ไทยต้อง subset** ฟอนต์ไทยชุดเต็มหนักกว่าฟอนต์ละตินมาก ให้ตัดเหลือเฉพาะ glyph ที่ใช้ ใช้ `font-display: swap` และจำกัดไม่เกิน 2 ตระกูล 3 น้ำหนักรวมทั้งเว็บ
- วิดีโอ: แสดง poster image ก่อน โหลดไฟล์เมื่อกดเล่นเท่านั้น และให้พิจารณาย้ายไปโฮสต์ที่ทำ adaptive streaming ถ้าคลิปยาวเกิน 1 นาที
- ไม่ใส่ script ของบุคคลที่สามเกินจำเป็น ถ้าต้องมี analytics ให้เลือกตัวที่เบา

## 8. SEO

เว็บเดิมข้อมูลอยู่ในรูปทั้งหมด ทำให้ค้นหาไม่เจอเลย ต้องแก้ตรงนี้เป็นอันดับต้น ๆ

- ทุกหน้าสินค้าเป็น HTML จริงที่มีชื่อ ราคา สเปกเป็น text
- ใส่ JSON-LD `Product` ในหน้าสินค้า และ `LocalBusiness` ในหน้า about (ร้านอยู่จันทบุรี ระบุให้ชัด)
- title และ description เขียนเป็นภาษาไทยตามที่คนค้นจริง เช่น "แหวนไพลินล้อมเพชร ทอง 18K ไซซ์ 52 — RG126"
- `alt` ของรูปเป็นภาษาไทยที่บรรยายของจริง ไม่ใช่ชื่อไฟล์
- มี sitemap.xml และ robots.txt
- **เช็คก่อนเริ่มงานว่าโดเมนปัจจุบันตอบ 404 ให้ bot หรือไม่** (ตอนตรวจสอบพบว่าดึงหน้าจากภายนอกไม่ได้ ขึ้น 404 ทั้งที่เปิดในเบราว์เซอร์ได้) ถ้ามีกฎบล็อกที่ CDN/WAF ต้องแก้ ไม่งั้น Google ก็เข้าไม่ได้เหมือนกัน

## 9. ข้อมูลสินค้าและระบบเพิ่มสินค้า

- เก็บใน Supabase โปรเจกต์เดียวกับ CRM แต่คนละตาราง (`products`)
- โครงฟิลด์ให้ล้อกับ `purchase_items` ใน `CLAUDE.md` เพื่อให้พนักงานกดบันทึกการขายแล้วดึงสเปกจาก `products` มาได้เลย ไม่ต้องพิมพ์ซ้ำ
- เว็บ build เป็น static ใช้ ISR revalidate เมื่อมีการแก้ข้อมูล

### หน้า admin เป็นของเดียวกับ CRM

**ห้ามสร้างระบบ admin แยกสองตัว** พนักงานต้องล็อกอินที่เดียว `admin.ruedeejewelry.com` แล้วมีทั้งเมนูลูกค้าและเมนูสินค้า
ใช้ตาราง `staff` และระบบสิทธิ์ชุดเดียวกับที่ระบุใน `CLAUDE.md`

### คนใช้งานคือใคร

พนักงานร้าน ไม่ใช่คนสายเทคนิค ใช้งานจาก**มือถือ ที่หน้าร้าน ทันทีหลังถ่ายรูปสินค้าเสร็จ** ไม่ใช่นั่งหน้าคอมกรอกทีละหน้าจอ
เกณฑ์ตัดสินว่าออกแบบสำเร็จ: **เพิ่มสินค้าใหม่หนึ่งชิ้นจนขึ้นเว็บได้ ภายใน 2 นาที บนมือถือ**

### กฎการออกแบบฟอร์มเพิ่มสินค้า

- **ฟิลด์บังคับให้น้อยที่สุด** บังคับแค่ รูป 1 รูป, ประเภท, ราคา ที่เหลือกรอกทีหลังได้
- **รหัสสินค้าให้ระบบสร้างให้อัตโนมัติ** ตามประเภท (RG สำหรับแหวน, ER ต่างหู, BR สร้อยข้อมือ, BC เข็มกลัด) พนักงานแก้ทับได้ถ้าร้านมีรหัสของตัวเองอยู่แล้ว
- **ทุกฟิลด์ที่ค่าซ้ำ ๆ ต้องเป็นปุ่มเลือก ไม่ใช่ช่องพิมพ์** ชนิดพลอย ชนิดทอง สี รูปทรง — ใช้ dropdown ที่มีค่าที่ร้านใช้จริงอยู่แล้ว และเพิ่มค่าใหม่ได้
- **ต้องมีปุ่ม "ทำซ้ำจากชิ้นนี้"** ในหน้าสินค้าฝั่ง admin ทุกชิ้น เพราะงานร้านส่วนใหญ่เป็นแบบเดียวกันแต่ต่างไซซ์หรือต่างสีพลอย กดแล้วได้ฟอร์มที่กรอกไว้ให้แล้ว เหลือแค่แก้ไซซ์กับราคา — ฟีเจอร์นี้ประหยัดเวลามากที่สุดในทั้งระบบ
- **บันทึกเป็นฉบับร่างได้** สถานะ `draft` ยังไม่ขึ้นเว็บ พนักงานถ่ายรูปอัปเดตไว้ก่อน แล้วเจ้าของมาเติมราคาทีหลัง
- **ไม่มี auto-save เงียบ ๆ** ต้องกดบันทึกเอง แต่ถ้ากดออกทั้งที่มีข้อมูลค้าง ให้เตือน
- ฟอร์มเรียงตามลำดับที่คนทำงานจริงคิด: รูป → ประเภท → ราคา → สเปกพลอย/ทอง → คำบรรยาย ไม่ใช่เรียงตามลำดับคอลัมน์ในฐานข้อมูล

### การจัดการรูป (จุดที่พังบ่อยที่สุด)

- อัปโหลดจากกล้องหรืออัลบั้มมือถือได้โดยตรง เลือกหลายรูปพร้อมกันได้
- **ย่อและบีบอัดรูปฝั่ง client ก่อนอัปโหลด** รูปจากมือถือใบละ 5–10 MB ถ้าอัปตรงจะช้าจนพนักงานเลิกใช้ และเปลืองพื้นที่เก็บ
- ครอปเป็นอัตราส่วนมาตรฐานของเว็บให้อัตโนมัติ พร้อมให้เลื่อนปรับตำแหน่งได้
- ลากสลับลำดับรูปได้ รูปแรกคือรูปหลักที่ขึ้นในกริด
- แสดงความคืบหน้าการอัปโหลด และถ้าเน็ตหลุดต้องไม่เสียข้อมูลที่กรอกไว้

### งานประจำวันที่ต้องเร็วเป็นพิเศษ

- **กด "ขายแล้ว" ต้องจบในแตะเดียวจากหน้ารายการ** ไม่ต้องเข้าไปหน้าแก้ไข นี่คือการกระทำที่ใช้บ่อยที่สุด
- แก้ราคาแบบเร็วจากหน้ารายการได้เช่นกัน (ทองขึ้นลงบ่อย)
- มีหน้ารายการที่กรองเห็น "ฉบับร่าง" และ "ยังไม่มีรูป" เพื่อไล่เก็บงานค้าง

### ความปลอดภัยและการกันพลาด

- พนักงานแก้และเพิ่มได้ **แต่ลบไม่ได้** ใช้ soft delete เจ้าของเท่านั้นที่ลบถาวรได้
- มีปุ่มดูตัวอย่างหน้าจริงก่อนเผยแพร่
- ทุกการแก้ไขเข้า `audit_log` เหมือนฝั่ง CRM
- เผยแพร่แล้วให้ยิง revalidate ไปที่หน้าเว็บที่เกี่ยวข้อง และ **แสดงผลให้พนักงานเห็นว่าขึ้นเว็บแล้วจริง** พร้อมลิงก์ไปหน้าจริง ถ้าไม่มีสัญญาณยืนยัน พนักงานจะไม่เชื่อว่าระบบทำงานแล้วกดซ้ำ

## 10. แนวทางการออกแบบ (สำหรับ Claude Design)

- **Mobile-first** ลูกค้าเกือบทั้งหมดมาจาก LINE, IG, TikTok บนมือถือ ออกแบบจอ 375–430px ก่อน แล้วค่อยขยาย
- กริดสินค้าบนมือถือ 2 คอลัมน์ ไม่ใช่ 1 เพราะคนต้องกวาดสายตาเปรียบเทียบได้
- โทน: ประณีต น่าเชื่อถือ อบอุ่น พื้นหลังเรียบ ปล่อยให้รูปเครื่องประดับเป็นพระเอก UI ถอยให้รูป
- ทองใช้เป็น accent เล็ก ๆ อย่าใช้เป็นสีหลักจนดูเชย
- ตัวอักษรราคาและรหัสสินค้าต้องอ่านชัดในระยะแขนบนมือถือ
- ภาษาไทยเป็นหลัก ภาษาอังกฤษใช้เท่าที่จำเป็น
- **sentence case ในภาษาอังกฤษ ห้าม ALL CAPS ทั้งบล็อก** ข้อความอังกฤษตัวพิมพ์ใหญ่เว้นระยะห่างแบบเว็บเดิมอ่านยากบนมือถือ
- ห้ามใช้ emoji ใน UI

### เรื่องเล่าของร้าน

เรื่องคุณแม่ฤดี งานที่ทำกันมาตั้งแต่รุ่นปู่ย่า ช่างมือดีของบ้าน และการอยู่จันทบุรีซึ่งเป็นตลาดพลอยใหญ่สุดของไทย — เป็นสิ่งที่ทำให้คนกล้าโอนเงินหลักแสน
อย่าเก็บไว้แค่หน้า about ให้มีเวอร์ชันย่อโผล่ในหน้าแรกและใกล้ปุ่ม CTA ในหน้าสินค้าด้วย
เนื้อหา FAQ ก็เช่นกัน คำถามที่เกี่ยวกับชิ้นนั้นโดยตรง (ปรับไซซ์ได้ไหม รับประกันยังไง ใส่อาบน้ำได้ไหม) ให้ยกไปวางในหน้าสินค้า ไม่ใช่ให้ลูกค้าเดินไปหาเองที่หน้า FAQ

## 11. ลำดับการทำ

1. ตาราง `products` + นำเข้าข้อมูลสินค้าที่มีอยู่
2. `/jewelry/[sku]` หน้าสินค้าเดี่ยว พร้อมปุ่มทัก LINE ที่พ่วงรหัส — ทำก่อนเพราะเป็นหน้าที่สร้างรายได้
3. **ฟอร์มเพิ่ม/แก้สินค้าฝั่ง admin พร้อมระบบอัปโหลดรูป** แล้วให้พนักงานลองใช้จริง 1 สัปดาห์ก่อนทำอย่างอื่นต่อ ถ้าพนักงานยังกรอกไม่ไหว ให้แก้ตรงนี้ให้จบก่อน อย่าเดินหน้าไปทำหน้าอื่น
4. `/jewelry` catalog + ฟิลเตอร์
5. หน้าแรก
6. `/series/[slug]` ย้ายซีรี่ย์แหวนปูมาใช้ข้อมูลชุดเดียวกัน
7. about, faq, ring-size
8. วัด performance จริงบนมือถือ แล้วแก้จนผ่านทุกตัวเลขในข้อ 7

## 12. เรื่องที่ยังไม่ตัดสินใจ

- ตอนนี้มีสินค้าทั้งหมดกี่ชิ้น และเพิ่มใหม่เดือนละประมาณกี่ชิ้น (มีผลกับการเลือก static ทั้งหมด vs ISR)
- พนักงานที่จะเป็นคนอัปเดตมีกี่คน และถนัดใช้มือถือหรือคอมมากกว่ากัน
- รูปสินค้าปัจจุบันเก็บที่ไหน ขนาดเท่าไหร่ ถ่ายมาตรฐานเดียวกันหรือไม่
- จะเก็บโดเมนเดิมและย้าย hosting หรือขึ้นใหม่คู่ขนานแล้วค่อยสลับ
